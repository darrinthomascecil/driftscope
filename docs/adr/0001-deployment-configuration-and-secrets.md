# ADR 0001 — Deployment configuration & secret management

- **Status:** Accepted
- **Date:** 2026-08-01
- **Deciders:** platform engineering
- **Supersedes:** the ad-hoc `terraform local_file` manifest codegen currently in `terraform/*.tf`

## Context

driftscope deploys to AKS via Kustomize + `kubectl`, with Azure infrastructure managed by
Terraform, secrets synced by External Secrets Operator (ESO) from Key Vault, and pods authenticating
to Azure via Workload Identity (WI). Per-deployment configuration — the public host, and Azure
identifiers (tenant id, group object id, managed-identity client ids, the Front Door GUID) — must
reach Kubernetes manifests somehow.

The current mechanism has accreted into a set of footguns, confirmed by inspection:

1. **Terraform writes manifests via `local_file`** (`params.yaml`, `patch-sa.yaml`,
   `external-secrets.yaml`, `edge/*`). This creates **dual ownership** — the file is both
   git-committed *and* generated by Terraform, which tracks the manifest's content in **Terraform
   state**. Any manual edit shows as drift; `terraform apply` silently overwrites committed files.
2. **Committed baselines are inconsistent.** `params.yaml` commits **live values** (`TENANT_ID`,
   `ALLOWED_GROUP_ID` are real, in git), while `patch-sa.yaml`/`external-secrets.yaml`/`edge/*`
   commit `REPLACE-*` placeholders. There is no single rule for what git should hold.
3. **Structural fields use positional Kustomize `replacements`** (`spec.servers.0.hosts.0`), which
   are brittle (reorder a Gateway server and the wrong field is patched, silently) and make the
   source file misrepresent what actually deploys.

These are safety and reproducibility hazards: a clone is not a clean template, real identifiers
leak into git, and no single component owns the deployed configuration.

## Decision

Adopt a strict three-layer separation. Each layer has exactly one owner and one mechanism; they
never mix.

| Layer | Contents | Owner / source of truth | Committed to git as | Never |
|---|---|---|---|---|
| **Structure** | manifests: routing, Deployments, policies | git (Kustomize base + `cloud` overlay) | static templates with `REPLACE-*` placeholders | a real value or a secret |
| **Non-secret config** | host, tenant/client/group ids, FD GUID | **Terraform outputs** | placeholders only | committed live; written by `terraform apply` |
| **Secrets** | client secrets, tokens | **Key Vault** → ESO + Workload Identity at runtime | *nothing* | in git, in a manifest, or in Terraform state |

Concretely:

1. **Terraform's responsibility ends at `outputs`.** It owns Azure infrastructure and *emits values*.
   It **does not write Kubernetes manifests** — the `local_file` resources for deploy YAML are
   removed. (Terraform state stops tracking manifest content.)
2. **The git repo is a pure template.** Every overlay file commits `REPLACE-*` placeholders only —
   including `params.yaml`. No deployment-specific identifier is ever committed.
3. **Values are bound at deploy time by the deploy pipeline** (`.github/workflows/deploy.yml`):
   it reads `terraform output -json` and materialises the `params` ConfigMap + SA/edge patches, then
   applies the overlay. The real values exist only within a pipeline run.
4. **Secrets remain ESO + Workload Identity.** No change — this layer is already correct.
5. **Kustomize is retained** as the manifest tool. For the one structural field that needs a value
   (the Gateway/VirtualService host), a single documented `replacement` reads the deploy-materialised
   `params` ConfigMap, guarded by a build-time consistency check (a test that the rendered
   Gateway/VirtualService host equals `params.HOST`).
6. **GitOps is the target deploy model.** A pull-based reconciler (Argo CD or Flux) becomes the
   enterprise endgame — drift detection + auto-heal, full audit, and no human running `kubectl`. The
   current push-based pipeline is the interim.

## Alternatives considered

- **Helm chart + values-from-Terraform-outputs.** Cleaner for injecting values into *structural*
  manifest fields (`{{ .Values.host }}` vs. positional Kustomize replacements), and the industry
  standard for parameterised Kubernetes. **Rejected for now:** the project is invested in Kustomize,
  and every *dangerous* footgun above (committed live values, dual ownership, Terraform-state-tracks-
  manifests) is tool-independent and fixed by the decision without switching tools. The remaining
  Kustomize weakness (positional replacement of one field) is a minor smell mitigated by a guard, not
  a reason to migrate the whole deploy system. Revisit if structural parameterisation grows.
- **Terraform manages Kubernetes objects directly** (`kubernetes_manifest` / `helm_release`). This is
  "Terraform owns the YAML state" done properly. **Rejected:** it couples Terraform to the cluster
  lifecycle, `kubernetes_manifest` is finicky with Istio CRDs and needs cluster access at plan time,
  and it conflicts with the intended GitOps endgame. Infrastructure (Terraform) and workload (GitOps)
  should stay separate control planes.

## Consequences

- **Positive:** the repo becomes a true clone-and-run template; no secret or live identifier is ever
  committed; `clone + tfvars + deploy` reproduces an identical deployment; Terraform and the deployer
  are cleanly separated; no component silently overwrites another.
- **Cost:** value injection moves into the deploy pipeline (one place to build and test). Local
  `kubectl apply -k` without the pipeline requires first materialising values from `terraform output`.
- **Neutral:** deployed output is unchanged — this is an ownership/safety refactor, not a behavioural
  one.

## Migration plan (phased — do not destabilise the working deployment)

1. **Now:** stop extending the anti-pattern. (Done — reverted the `istio-routing.yaml` `local_file`
   experiment; `local_file` is not expanded to new manifests.)
2. **Templatise git:** make every committed overlay `REPLACE-*` placeholders, including
   `params.yaml` (remove the live tenant/group ids). **Done.**
3. **Move injection to the pipeline:** render `params` + SA/edge patches from `terraform output`
   at deploy; add the host-consistency guard test. **Done** (`deploy/gitops/render-overlay.sh`).
4. **Remove Terraform `local_file` manifest resources.** **Done for the app overlay** — the three
   app-overlay `local_file` resources (`params`, `patch_sa`, `external_secrets`) and their templates
   are deleted; `render-overlay.sh` is now the *single* renderer for the app overlay across the
   bootstrap, CI, and Argo CD, and the stale hardcoded ACR (`kustomization.yaml`) + host
   (`istio-routing.yaml`) are placeholders. The image registry is a `REPLACE-IMAGE-REPO` placeholder
   bound from `acr_login_server`; the tag lives in git. **Remaining:** the `edge/` `local_file`
   resources (cert-manager DNS-01 issuer, origin cert, X-Azure-FDID origin lock) — single-mechanism,
   custom-domain-only — are a scoped follow-up.
   - **State migration (existing deployments):** `local_file` *deletes its file on destroy*, so
     `terraform apply` after this change would remove the now-committed templates from the working
     tree. Before applying, forget the resources so Terraform won't delete the files:
     `terraform state rm local_file.params local_file.patch_sa local_file.external_secrets`.
     Fresh deployments (no prior state) are unaffected — the resources simply never existed.
5. **GitOps:** introduce Argo CD (or Flux) reconciling the overlay; retire imperative `kubectl`.
   (ADR 0002 — Argo installed + reconciling; auto-sync cutover gated on the image-tag-in-git change.)

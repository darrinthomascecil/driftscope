# Image signing (keyless, Sigstore)

driftscope clones and reads customers' **private** repositories. The container that does that must
be **provably the one this repo built** — not a look-alike someone else pushed to the registry. So
every published image is **cryptographically signed**, and the signature is checkable by anyone,
with no shared secret.

## How it works — keyless

`.github/workflows/release.yml` builds the image, pushes it to GHCR, and signs it with
[cosign](https://docs.sigstore.dev/) in **keyless** mode:

1. The workflow requests a short-lived **GitHub OIDC token** (`id-token: write`). Its subject is
   *"the `release.yml` workflow in `darrinthomascecil/driftscope`, at this ref."*
2. cosign exchanges that token at **Fulcio** for a short-lived X.509 signing certificate bound to
   that identity, signs the image **digest**, and records the signature in the **Rekor** public
   transparency log. The certificate expires in minutes; nothing secret is stored.
3. Verification checks that the signature chains to a Fulcio cert whose identity is this repo's
   release workflow, issued by GitHub's OIDC — i.e. *"GitHub attests this workflow produced this
   exact digest."*

There is **no private key** to store, rotate, or leak. The trust root is the identity, not a
secret. (The alternative — a long-lived key in Azure Key Vault — is viable given driftscope already
uses KV for JWT signing; it was rejected here because keyless removes the key-custody problem
entirely and is verifiable in CI with no cloud credentials. See the PR discussion.)

## What gets signed

- **The image**, by **digest** (`…@sha256:…`), never by tag. A tag can be re-pointed at a different
  image *after* signing; a digest cannot — pinning to the digest is the entire point.
- **An SPDX SBOM**, generated by [syft](https://github.com/anchore/syft) and attached as a signed
  **attestation** (`cosign attest --type spdxjson`), so a consumer can see (and trust) exactly
  what is in the image.

The workflow then **verifies both in-CI** — a signature nobody checks is theatre. If the release
run is green, the same verification will succeed for anyone else.

## Verify an image yourself

No secrets required:

```bash
make verify-image IMAGE=ghcr.io/darrinthomascecil/driftscope:<tag>
```

or directly:

```bash
cosign verify \
  --certificate-identity-regexp '^https://github.com/darrinthomascecil/driftscope/\.github/workflows/release\.yml@refs/tags/v' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  ghcr.io/darrinthomascecil/driftscope:<tag>

cosign verify-attestation --type spdxjson \
  --certificate-identity-regexp '^https://github.com/darrinthomascecil/driftscope/\.github/workflows/release\.yml@refs/tags/v' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  ghcr.io/darrinthomascecil/driftscope:<tag>
```

The identity regexp restricts trust to **release-tag** builds. PR builds are signed too (that is how
the pipeline is proven before merge), but with a `refs/pull/…` identity — so the default consumer
check above will *not* accept a PR image, only a tagged release.

## Releasing

A signed release is cut by pushing a semver tag:

```bash
git tag v0.1.0 && git push origin v0.1.0
```

That publishes `v0.1.0`, `v0.1`, and `latest`, all signed. On a pull request the same chain runs
against a `pr-N` / `sha-…` tag to prove it works, without claiming a release.

## Scope & follow-ups

This signs the image driftscope **publishes**. It is deliberately one layer of the supply chain,
not all of it. The natural next steps (roadmap Phase 1):

- **Sign the deployed artifact.** The AKS bootstrap builds the running image with `az acr build`
  into ACR (`scripts/bootstrap/image.sh`); wiring signing into that path signs what actually runs.
- **Admission enforcement.** A cluster policy (Ratify / Kyverno `verifyImages`) that **refuses to
  run an unsigned image** turns the signature from evidence into a gate.
- **Pin CI actions by commit SHA** + Dependabot, so the signing pipeline itself has a pinned,
  auditable supply chain. (Today they are pinned to major version tags for readability.)
